# bb mobile entry

`/mobile` is a second Vite entry of the real `@bb/app` frontend. It is not a separate client and must not reimplement bb's server contracts with hand-written `fetch` calls.

## Shared with full bb

The mobile entry intentionally reuses bb's authoritative frontend seams:

- `createAppQueryClient` and browser lifecycle behavior
- `useWebSocket` realtime cache invalidation
- `useAppTheme` plus the normal `app.css` / `theme.css` tokens
- `useSidebarNavigation` (`sidebar-bootstrap`) for projects and thread membership
- bb route helpers and route-state parsing
- `useThread`, `useThreadDetailBootstrap`, `useThreadTimeline`, and pending-interaction queries
- `ThreadTimelineSurface` for the conversation/activity renderer
- bb mutations for send, stop, read state, and interaction resolution

This prevents the mobile UI from observing a different set of threads or interpreting thread state differently from the desktop app.

## Intentionally excluded from initial mobile startup

The mobile entry does not mount `App`, `AppLayout`, `SplitThreadArea`, or `ThreadDetailView`. Those roots pull in desktop workspace systems that are not required for the primary phone workflow: split panes, terminals, secondary browser/file panels, plugin panel boot, rich desktop chrome, and related orchestration.

The mobile composer is intentionally a lean text composer. Full rich composer behavior, model/provider controls, attachments, terminal/file panels, and plugin panels remain available by opening full bb until they can be shared without restoring the desktop startup cost.

The native timeline file-diff renderer is lazy-loaded so `@pierre/diffs` is not part of the initial mobile path.

## Routing

The mobile entry uses `HashRouter`, but the route *inside the hash* is a normal bb route generated by `getThreadRoutePath`. This lets native timeline links navigate with bb semantics while keeping the server request at `/mobile/index.html`.

Examples:

```text
/mobile/index.html?build=shared-core-1#/
/mobile/index.html?build=shared-core-1#/projects/<projectId>/threads/<threadId>
/mobile/index.html?build=shared-core-1#/threads/<personalThreadId>
```

## Build and verification

From the repository root:

```bash
pnpm --filter @bb/app verify:mobile
pnpm --filter @bb/app typecheck
pnpm --filter @bb/app build
```

After build, verify `apps/app/dist/mobile/index.html` exists and inspect the generated entry/chunk sizes. A mobile performance change is not complete until it is tested from the installed iPhone PWA and compared against the same thread in full bb.

## Guardrail

Do not add another `apps/mobile` application or `public/mobile/core.js` / `views.js` / `data.js` implementation. `pnpm --filter @bb/app verify:mobile` explicitly rejects the obsolete standalone-client architecture.
